Configuración y utilización de la autenticación con token.

## Introducción

El JWT (JSON Web Token) es un estándar para garantizar la seguridad y el contexto de la autenticación en aplicaciones web, donde el frontend se encuentra desacoplado del backend.

Es común utilizarlo cuando el frontend de una aplicación web está desarrollado en ReactJS, AngularJS, VueJS, etc., y el backend proporciona una API REST para proporcionar y recibir datos dinámicos de la aplicación.

> El token (JWT) es un código seguro que identifica al usuario.

Con el JWT (JSON Web Token), la API REST del backend permite a los servicios privados obtener el contexto de autenticación, para saber quién es el usuario autenticado, es decir, a partir del token podemos saber cuál es el usuario, siendo que el token en este caso es JWT (JSON Web Token).

## CORS

La API REST puede estar en un subdominio diferente del sitio web, lo que implica configuraciones de [CORS (Cross-Origin Resource Sharing)](/docs/academy/server/services/cors) para que se pueda acceder a los servicios.

Por lo tanto, si la API REST está en un dominio/subdominio diferente del frontend, incluso utilizando JWT, es necesario que CORS esté configurado correctamente.

> CORS es una política de seguridad para el consumo de recursos en dominios, subdominios o puertos diferentes.
> Para garantizar que una dirección puede realmente integrarse con otra dirección.

Esto ocurre debido a que los navegadores bloquean la utilización de servicios, u otros tipos de recursos, en direcciones externas, con el objetivo de evitar ataques de obtención de datos confidenciales.

## Activación y Configuración

Para activar y configurar el JWT en su aplicación en Netuno, es necesario editar el archivo de configuración de la aplicación correspondiente al entorno que está utilizando, como:

- `config/_development.json`
- `config/_production.json`

> Depende del entorno configurado en Netuno, en el archivo `netuno/config.js` ver la parametrización de `config.env`.

Inserte y ajuste los siguientes parámetros:

```json
    ...
    "auth": {
        "jwt": {
            "enabled": true,
            "secret": "SecretoTieneQueTener32Caracteres!!!",
            "expires": {
                "access": 1440,
                "refresh": 1440
            }
        }
    },
    ...
```

En el parámetro `secret` coloque una secuencia de caracteres compleja y aleatoria, es la clave que garantizará la seguridad del cifrado del JWT.

Los parámetros de `expires` se definen en minutos, por ejemplo: `60` que equivale a 1 hora y `1440` a un día.

### Acceso Restringido a Grupos

Adicionalmente se puede pasar el parámetro `groups`, que define el código de Grupos de los usuarios que pueden autenticarse con JWT, por ejemplo:

```json
    ...
    "auth": {
        "jwt": {
            ...
            "groups": ["cliente", "proveedor"],
            ...
        }
    },
    ...
```

En el ejemplo anterior, solo los usuarios que pertenecen a los grupos de:

- Clientes, siendo el código del grupo `cliente`.
- Proveedores, siendo el código del grupo `proveedor`

Solo los usuarios en estos grupos pueden autenticarse con JWT.

## Fetch - JavaScript Puro

JavaScript en los navegadores proporciona `fetch` para integrarse con los servicios de la API REST del backend.

A continuación, algunos ejemplos de cómo realizar la autenticación con JWT y la renovación del token.

### Autenticación

Ejemplo de cómo obtener el _Access Token_ con [fetch](https://developer.mozilla.org/pt-BR/docs/Web/API/Fetch_API):

```javascript
fetch("http://localhost:9000/services/_auth", {
    method: 'post',
    headers: {
        'Content-Type': 'application/json',
        'Accept': 'application/json'
    },
    body: JSON.stringify({
        username: payload.username,
        password: payload.password,
        jwt: true
    })
}).then((response) => {
	if (response.status != 200) {
        if (response.status != 403) {
            console.log('La autenticación falló con el estado inesperado:', response.status);
        }
        alert('Login inválido.');
        return null;
    }
    return response.json();
}).then((res) => {
    if (res && res.result === true) {
        console.log(`Mi Access Token: ${res.access_token}`);
        console.log(`Mi Refresh Token: ${res.refresh_token}`);
        console.log(`Expira en: ${res.expires_in} minutos`);
        sessionStorage.setItem('token', JSON.stringify(res));
    }
}).catch((error)=> {
    console.log(error);
    alert('Hubo un problema técnico, inténtelo de nuevo más tarde.');
});
```

Tenga en cuenta que el `token` deberá guardarse como sesión, por lo tanto, es preferible utilizar [sessionStorage](https://developer.mozilla.org/pt-BR/docs/Web/API/Storage) en lugar de [localStorage](https://developer.mozilla.org/pt-BR/docs/Web/API/Storage) para mayor seguridad.

Con el `refresh_token` es posible generar un nuevo `token` antes del tiempo de expiración (`expires_in` en minutos).

### Utilizar el _Access Token_ en otros Servicios

Para ejecutar servicios programados a medida que requieran autenticación previa en aplicaciones Netuno, debe pasar el _Access Token_ en el Header del protocolo HTTP, como valor de la clave _Authorization_, por ejemplo:

`Authorization: Bearer eyJhbGciOiJIUzU...`

Ejemplo de cómo ejecutar un servicio programado a medida a través del frontend utilizando [fetch](https://developer.mozilla.org/pt-BR/docs/Web/API/Fetch_API), donde el `Authorization` se pasa en los `headers`:

```javascript
const token = JSON.parse(sessionStorage.getItem("token"));

fetch("http://localhost:9000/services/mi-servicio", {
    method: 'post',
    credentials: 'include',
    headers: {
        'Authorization': `${token.token_type} ${token.access_token}`,
        'Content-Type': 'application/json'
    },
    body: JSON.stringify({
        miParametro1: '...',
        miParametro2: '...'
    })
}).then((response) => {
    if (response.status != 200) {
    	console.log(`El servicio falló con el estado ${response.status}.`);
        if (response.status == 403) {
            alert('No autenticado.');
        } else {
            alert('Hubo un fallo con el servicio.');
        }
        return null;
    }
    return response.json();
}).then((res) => {
    if (res) {
        console.log(`Datos de respuesta de mi servicio:`, res);
        alert('Servicio ejecutado con éxito.');
    }
}).catch((error)=> {
    console.log(error);
    alert('Hubo un problema técnico, inténtelo de nuevo más tarde.');
});
```

Tenga en cuenta que, en los Headers del HTTP, en el parámetro `Authorization` se utiliza el `token_type` y el `access_token` obtenidos del objeto JWT guardado previamente en la autenticación en [sessionStorage](https://developer.mozilla.org/pt-BR/docs/Web/API/Storage).

### Actualizar con el _Refresh Token_

Para actualizar el token y prolongar la autenticación, debe llamar nuevamente al servicio `_auth`, pero además del parámetro `jwt: true` es necesario pasar también el parámetro `refresh_token` con el valor recibido en la autenticación exitosa anterior.

La actualización del token debe realizarse antes del tiempo de expiración (`expires_in` en minutos).

Entonces, para prolongar la autenticación y renovar el token, vea el ejemplo:

```javascript
const token = JSON.parse(sessionStorage.getItem("token"));

fetch("http://localhost:9000/services/_auth", {
    method: 'post',
    headers: {
        'Content-Type': 'application/json',
        'Accept': 'application/json'
    },
    body: JSON.stringify({
        refresh_token: token.refresh_token,
        jwt: true
    })
}).then((response) => {
    if (response.status != 200) {
        if (response.status != 403) {
            console.log('La renovación del token falló con el estado inesperado:', response.status);
        }
        alert('Renovación del acceso con token inválido.');
        return null;
    }
    return response.json();
}).then((res) => {
    if (res && res.result === true) {
        console.log(`Mi Nuevo Access Token: ${res.access_token}`);
        console.log(`Mi Nuevo Refresh Token: ${res.refresh_token}`);
        console.log(`Expira en: ${res.expires_in} minutos`);
        sessionStorage.setItem("token", JSON.stringify(res));
    }
}).catch((error)=> {
    console.log(error);
    alert('Hubo un problema técnico, inténtelo de nuevo más tarde.');
});
```

Al obtener el nuevo token debe pasar a utilizarlo, en lugar del anterior (antiguo) en las próximas llamadas a los servicios.

De esta forma, la autenticación se prolonga con sucesivas renovaciones del token, es una forma de garantizar que el usuario continúa autenticado.

## Auth Client - NPM

Para realizar fácilmente la integración con el frontend se proporciona el módulo de NPM:

- [@netuno/auth-client](https://www.npmjs.com/package/@netuno/auth-client)

En el frontend puede realizar la instalación con [Bun](https://bun.sh):

- `bun install @netuno/auth-client`

> Se puede utilizar otro gestor de dependencias de frontend como PNPM, NPM, YARN, u otro.

### Configuración

Este módulo depende de [@netuno/service-client](https://www.npmjs.com/package/@netuno/service-client), al definir la dirección de los servicios, por ejemplo:

```javascript
import _service from '@netuno/service-client';
...
_service.config({
    prefix: 'http://localhost:9000/services/'
});
```

El `auth-client` utiliza el prefijo del `service-client` para construir internamente la dirección del servicio `_auth`, en este caso, siguiendo el ejemplo será:

- `http://localhost:9000/services/_auth`

Entonces, esta dirección se construye automáticamente utilizando el prefijo de dirección de los servicios de la API REST de la aplicación Netuno.

Vea cómo personalizar las configuraciones del `auth-client`:

En la versión ES module, `config()` es asíncrono. Espere a que finalice antes de utilizar el cliente configurado:

```javascript
import _auth from '@netuno/auth-client';

await _auth.config({
    storage: 'local', // session es el valor predeterminado.
    onLogin: () => { alert("¡Sesión iniciada!"); },
    onLogout: () => { alert("¡Sesión cerrada!"); }
});
```

Si desea que el token se guarde en `localStorage`, entonces es necesario definir en la configuración `storage: 'local'`, porque por defecto es `storage: 'session'` utilizando `sessionStorage`.

### Autenticación

Para efectuar el login utilizando el `_auth`:

```javascript
import _auth from '@netuno/auth-client';
...
_auth.login({
    username: "admin",
    password: "secret",
    success: ()=> {
        alert("Éxito.");
    },
    fail: ()=> {
        alert("Fallo.");
    }
});
```

El token se guarda automáticamente, en `session` (`sessionStorage`) o `local` (`localStorage`), dependiendo de la configuración, por defecto es `session`.

### Actualizar el Token

Ejemplo de cómo actualizar el token:

```javascript
import _auth from '@netuno/auth-client';
...
_auth.refreshToken({
    success: ()=> {
        alert("Éxito.");
    },
    fail: ()=> {
        alert("Fallo.");
    }
});
```

El token se guarda automáticamente, en `session` (`sessionStorage`) o `local` (`localStorage`), dependiendo de la configuración, por defecto es `session`.

### Eliminar el Token

Ejemplo de cómo terminar la sesión, es decir, el proceso de salir y eliminar el token:

```javascript
import _auth from '@netuno/auth-client';
...
_auth.logout();
```

El token se elimina del `sessionStorage` o del `localStorage` dependiendo de la configuración, el estándar es `sessionStorage`.

## Backend - Servicios de la API REST

Si el header `Authorization` se pasa en la integración con los servicios con un token válido, entonces es posible identificar cuál es el usuario y el grupo.

En el backend podemos utilizar el recurso `_user` y el `_group`, que identifican cuál es el usuario y el grupo respectivamente.

Para ver los datos del usuario autenticado utilizamos el recurso [User](/docs/library/resources/user), por ejemplo:

### Seguridad

Si el token es inválido, o si no se pasa el `Authorization`, entonces Netuno garantiza que el servicio no se ejecuta, excepto si el servicio está configurado como acceso público, por defecto los servicios son privados.

> Para gestionar si el servicio es público o privado, configure en su aplicación en: `server/core/_service_config.js`

Siendo que en desarrollo Netuno permite ejecutar los servicios privados directamente sin autenticación, por cuestiones de practicidad, porque la mayoría de los servicios programados normalmente no necesitan el contexto de autenticación, entonces se vuelve más simple en general el desarrollo y las pruebas.

Si no es en desarrollo, por ejemplo en producción, entonces los servicios solo pueden ejecutarse con autenticación, como es obvio.

### Recurso de Autenticación

Normalmente el recurso `_user` y `_group` son suficientes, pero hay situaciones en las que queremos realizar operaciones más avanzadas y en este caso tenemos el recurso `_auth`.

El recurso `_auth` es el recurso principal de autenticación, gestiona las configuraciones y tiene todas las operaciones relacionadas con el proceso de autenticación.

> Para saber más, vea la documentación del recurso [Auth](/docs/library/resources/auth).

## ReAuthKit

Netuno proporciona un proyecto base para crear plataformas con autenticación en línea, que tiene la creación de cuenta, login, perfil, avatar, recuperación de contraseña, y mucho más.

Compruébalo en GitHub:

- [ReAuthKit](https://github.com/netuno-org/reauthkit)

> ReAuthKit es una aplicación Netuno con el frontend hecho en React, Ant.Design y React Router, y la base de datos en PostgreSQL.

Con ReAuthKit se acelera mucho la creación de nuevos proyectos con autenticación, porque ya tiene todos los mecanismos necesarios para cualquier proyecto que necesite autenticación.

## Conclusión

De forma simple, es posible configurar y activar la autenticación con JWT (JSON Web Token) en las aplicaciones.

> Utilice la autenticación con JWT para desarrollar servicios seguros en la API REST.

La integración del JWT en el frontend puede ser utilizando directamente con `fetch`.

Para agilizar y estandarizar la implementación se proporciona el módulo NPM [@netuno/auth-client](https://www.npmjs.com/package/@netuno/auth-client), que puede ser utilizado con cualquier tecnología de frontend.

Siempre que sea necesario identificar al usuario en la ejecución de servicios de la API REST utilice la autenticación con JWT.

En el backend es muy simple la configuración y la obtención del usuario autenticado.
